# 런북 — 시트 · 동기화 운영 (행 순서 · 안전 정지 · 알림)

> 근거: 2026-11-19 운영 사고와 그 대응(#257 · #258 · #260 · #264). 실데이터(시트 · DB) 작업은 모두 사용자가 직접 한다 — `.claude/rules/data-safety.md`.

DB 는 주문을 **시트 행 번호**(`sheet_row_number`)로 기억한다. 시트 행 순서가 바뀌면 DB 와 시트가 어긋난다.
v2.4.0 부터 앱은 어긋남을 감지하면 **쓰지 않고 멈춘다**(안전 정지). 이 런북은 그 신호를 읽고 정리하는 절차다.

## 운영 원칙

1. **응답 시트에서 주문 행을 지우지 않는다** — 취소 · 중복은 웹에서 삭제(시트 `삭제됨` 칸에 표시된다)
2. **응답 시트에 손으로 행을 넣지 않는다** — 구글 폼은 새 응답을 "마지막 폼 응답 바로 아래"에 끼워 넣어, 폼 영역 밖 행을 아래로 민다. 손 주문 · 배송사고는 웹에서 만든다(배송사고는 DB 전용)
3. **행을 정렬 · 이동하지 않는다** — 정렬 · 필터 보기는 별도 탭이나 필터 보기로
4. 시트의 `DB_SYNC_STATUS` · `DB_SYNC_AT` · `DB_SYNC_ID` 칸은 동기화가 쓴다 — 아래 정리 절차 밖에서는 고치지 않는다
5. **hybrid 정본은 DB 다 (#281 · 2026-11-19)** — 시트 → DB 는 새 주문이 처음 들어올 때만 쓴다. 상태 · 송장 · 수취인 수정 · 삭제는 **웹에서만** 한다. 응답 시트의 주문 칸을 손으로 고쳐도 DB 에 반영되지 않는다(시트 `삭제됨` 표시도 마찬가지)
6. 주문자가 처음 입력한 값은 주문이 만들어질 때 DB(`original_input`)에 보관되어 주문 상세 "최초 입력값" 에서 볼 수 있다. 이 기능 이전 주문은 보관된 값이 없다

| 웹 토스트 "구글 시트의 행 순서가 DB 와 맞지 않아 저장하지 않았습니다" | 웹 수정 대상 행이 다른 주문이다(409 · 변경 없음) | 토스트의 행 번호 |

| DB `sync_error_message` 가 `sheet-write-pending:…` 로 시작 (#293) | 웹 쓰기가 DB 를 쓰기 전에 남기는 "시트 반영 대기" 표시. 시트까지 성공하면 바로 지워진다. 5분 넘게 남아 있으면 쓰기 도중 api 가 끝난 것 | 손댈 것 없음 — 5분이 지나면 재조정이 DB 값으로 시트를 맞추고 지운다. 그동안 시트 우선 가져오기는 그 주문을 덮지 않는다(재조정 대기) |
| DB `sync_error_message` = `sheet-write-pending:superseded` (#304) | 끝나지 않았거나(api 종료) 동시에 진행 중인 웹 쓰기의 대기 표시 위에 다른 웹 쓰기가 왔다 — 어느 쓰기도 지우지 않는다 | 손댈 것 없음 — 5분 뒤 재조정이 행 전체를 DB 값으로 맞추고 지운다 |
| 시트 `DB_SYNC_STATUS = fail` | 그 행은 동기화되지 않았다 | 매분 재시도 중 |
| 신규 폼 주문이 웹에 안 보임 · 알림 없음 | 그 행이 안전 정지됐을 수 있다 | 위 신호와 함께 |

> 앱 로그: pm2 fork 모드 전환(#256 · `auto-deploy.md`) 전에는 pm2 에 남지 않는다 — 전환 뒤에는 `pm2 logs myTangerineSync` 에서
> `Row identity conflict` · `Scheduled sync completed` 를 볼 수 있다.

## 진단 — DB 와 시트 대조 (읽기만)

알림 · 토스트의 행 번호 주변을 DB 와 시트로 나란히 본다.

```bash
sudo -u postgres psql -d mytangerine -c "SELECT sheet_row_number AS row, id, timestamp_raw, order_type, status, deleted_at IS NOT NULL AS deleted FROM orders WHERE sheet_row_number BETWEEN <시작> AND <끝> ORDER BY sheet_row_number;"
```

> **시각 조건은 UTC 로 비교한다.** DB 시각 칸(`updated_at` · `created_at` · `changed_at` …)은 시간대 없는 `timestamp` 에 **UTC** 로 저장되고,
> 운영 psql 세션 시간대는 `Asia/Seoul` 이다(2026-11-20 확인). `updated_at > now() - interval '1 hour'` 는 9시간 어긋나 비어 나온다 —
> `updated_at > (now() AT TIME ZONE 'UTC') - interval '1 hour'` 로 쓴다. 결과의 시각도 UTC 다(한국 시각 = +9시간).

시트의 같은 행 범위 `타임스탬프` 칸과 한 줄씩 비교한다. 대표 모양:

| 모양 | 원인 | 정리 |
|---|---|---|
| DB 의 행 N 주문이 시트 N+k 에 있다(아래로 밀림) | 폼 영역 밖 행 위로 폼 응답이 끼워짐 · 행 삽입 | **A** |
| DB 의 행 N 주문이 시트 N−k 에 있다(위로 당겨짐) | 중간 행 삭제 | **B** |
| DB 의 행 N 주문이 시트 어디에도 없다 · 그 자리에 새 주문 | 마지막 행 삭제 뒤 번호 재사용 | 자동 — 동기화가 예전 주문을 보존한 채 분리하고 새 주문을 만든다(24시간 3건 상한) |

## 정리 A — 폼 영역 밖 행이 밀린 경우 (2026-11-19 사례)

폼 영역 밖 행(예: 1월 7일 시트 모드 시절 웹이 추가한 배송사고 행)을 **응답 시트 밖으로 뺀다.** 그 행이 남아 있는 한 폼 응답마다 다시 밀린다.

1. 밀린 행 위에 끼워진 새 주문들이 안전 정지됐다면 — 그 주문들은 정리 뒤 동기화가 다시 들여온다
2. 밀린 행이 **DB 전용으로 가야 하는 주문**(배송사고)이면 — 먼저 그 주문의 DB 레코드가 있는지 본다(시트 `타임스탬프` 원문으로):
   ```bash
   sudo -u postgres psql -d mytangerine -c "SELECT id, sheet_row_number, order_type, status, deleted_at IS NOT NULL AS deleted FROM orders WHERE timestamp_raw = '<시트 타임스탬프 원문>';"
   ```
   원문 표기가 조금 달라(점 · 공백) 안 나오면 날짜로 좁혀 본다: `… WHERE timestamp >= '<날짜>' AND timestamp < '<다음 날>' AND order_type = 'claim'` (#266)
   - **레코드가 있으면(보통 — v2.4.0 이후는 덮어쓰지 않는다):** 다시 만들 필요 없다. 그 id 를 **DB 에 기록된 행 번호 그대로** 분리한다.
     동기화 칸을 비워 다시 만들게 하지 않는다 — 같은 주문이 DB 에 있어 중복 방지로 멈춘다
     1. `pm2 stop myTangerineSync`
     2. 백업 → 분리:
        ```bash
        sudo -u postgres pg_dump -Fc mytangerine > ~/mytangerine-$(date +%Y%m%d-%H%M)-before-detach.dump
        sudo -u postgres psql -d mytangerine -c "UPDATE orders SET sheet_row_number = NULL WHERE id = <id> AND sheet_row_number = <DB 에 기록된 행> AND order_type = 'claim';"   # UPDATE 1 이어야 한다
        ```
   - **레코드가 없으면(v2.4.0 이전 사고로 덮어써짐 — 2026-11-19 사례):** 시트 원본으로 다시 만든 뒤 분리한다
     1. 시트 그 행의 `DB_SYNC_STATUS` · `DB_SYNC_ID` 를 비우고 1~2분 기다린다 → 위 조회로 새 id 와 행 번호(= 지금 시트 행)를 확인
     2. `pm2 stop myTangerineSync` → 백업 → 위 UPDATE 를 새 id · 지금 시트 행으로 실행(UPDATE 1)
   - 이어서(두 경우 공통):
     1. 시트에서 그 행을 잘라 별도 탭(예: `배송사고_이전`)에 붙이고 응답 시트에서 삭제한다(맨 마지막 행일 때만 — 아니면 B 처럼 다룬다)
     2. `pm2 start myTangerineSync` — 그 행 번호에 막혀 있던 새 주문들이 다음 회차에 들어온다
3. 잘못 덮어써진 DB 주문이 있으면(v2.4.0 이전 사고) 시트 원본으로 되살린다 — 사례: 테스트 주문은 웹에서 삭제, 실제 주문은 위 2 처럼 다시 만들기

## 정리 B — 중간 행이 지워진 경우

가장 안전한 정리는 **시트를 되돌리는 것**이다.

1. 시트 **파일 → 버전 기록**에서 삭제 직전 버전을 찾아 지운 행을 되살린다(행 순서가 원래대로 돌아오면 DB 와 다시 맞는다)
2. 그 행이 정말 없어져야 하는 주문이면 웹에서 삭제한다(`삭제됨` 표시 — 행은 남는다)
3. 되돌릴 수 없으면(이후 폼 응답이 많이 쌓임) DB 의 행 번호를 시트에 맞춰 다시 매겨야 한다 — **손 SQL 로 하지 말고** 이슈를 열어 재정렬 절차를 함께 정한다(자동 재정렬은 아직 없다)

## 복구 — 시트 우선 전체 가져오기 (운영자 전용 · #281)

평소 동기화는 기존 주문을 바꾸지 않는다. DB 장애로 hybrid 가 시트로 폴백했거나 sheets 모드로 운영한 뒤처럼 **DB 가 시트보다 뒤처졌을 때만** DB 를 시트 값에 맞춘다.

- 실행(서버에서 · 웹 버튼 없음 · 값은 `.env` 에서 셸로 읽는다 — 출력하지 않는다):
  ```bash
  curl -sS -X POST "http://127.0.0.1:${PORT}/api/sync/full" \
    -H "x-api-key: ${API_SECRET_KEY}" -H "x-app-client: sync-service" \
    -H "content-type: application/json" -d '{"confirm":"sheet-first"}'
  ```
- 주문마다 한 트랜잭션으로 덮어쓰고 **바뀐 필드 전체**(상태 · 송장 · 삭제 · 주문유형 · 상품 · 수량 · 주문자 · 보내는분 · 받으실분)를 변경 이력(`changedBy=sync`)에 남긴다. 실행이 시트를 읽은 뒤(또는 읽기 10분 전부터) 웹에서 고친 주문은 낡은 시트 값으로 덮지 않고 실패로 보고한다(시트 상태 칸도 쓰지 않는다 · 잠시 뒤 다시 실행하면 그때의 시트로 판단 · #228). 최초 입력값은 바꾸지 않는다
- 덮어쓰지 않는 주문(응답 `pendingReconcileRows` · 로그 `left for reconcile` 로 보고): 시트 반영 실패 표시가 있는 주문(DB 에만 있는 변경). 재조정(#231)이 DB 값을 시트에 쓴 뒤 다시 실행하면 그 주문도 시트 값에 맞춰진다
- **웹에서 고친 주문도 시트 값으로 덮어쓴다(#228)** — 웹 수정은 보통 시트에도 반영돼 있어 값이 바뀌지 않는다. 시트가 웹 수정 이전 값이면 그 값으로 돌아가므로, 실행 전 시트가 정답인지 확인한다(바뀐 필드는 변경 이력에 남는다)
- **`DATA_SOURCE=database` 로 운영한 뒤에는 실행하지 않는다** — 그 기간의 웹 수정은 시트에 쓰이지 않았고 시트 반영 실패 표시도 없어, 가져오기가 시트의 낡은 값으로 되돌린다
- 웹-시트 "충돌" 개념은 없다(#228) — 예전 충돌 로그는 이력 탭에 그대로 보인다
- 실행 전 `pg_dump` 백업을 남긴다(data-safety S-3)
- 평소 증분 동기화는 시트 값이 DB 와 다른 행을 DB 그대로 두고 응답 `sheetDivergedRows` · 로그(`Sheet row differs from the DB order`)로 알린다 — 시트 반영 실패(웹 경고 "부분 저장") 뒤 자연스럽게 생긴다
- sheets 모드로 운영하던 기간에 들어온 주문은 hybrid 로 바꾼 뒤 처음 DB 에 만들어진다 — 그 주문의 최초 입력값은 그 시점의 시트 값이다

## 교체 상한 · 동기화 정지가 풀리는 조건

- 행 정체성 충돌로 멈춘 행은 정리가 끝나면 다음 cron(1분)에 스스로 풀린다
- 교체 상한(24시간 3건)에 걸린 행은 최근 교체 3건이 24시간 밖으로 나가야 다시 교체된다 — 그 사이 같은 신호가 계속되면 오판일 수 있으니 진단부터 한다
- `#hermes` 경고는 종류별 하루 1회다 — 다음 날 같은 경고가 오면 아직 안 풀린 것이다
